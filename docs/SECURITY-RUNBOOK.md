# Безопасность Fastburgers: развёртывание, откат и действия во внешних панелях

Документ для владельца проекта. Здесь только то, что подготовлено в коде и что нужно сделать вручную. **Ничего из внешних настроек
(Vercel, GitHub, MongoDB Atlas) не включено и не проверено, пока вы сами не подтвердите это.** Названия пунктов меню могут
отличаться в зависимости от тарифа и версии интерфейса.

## 1. Что где лежит

| Ветка | Содержимое | Статус |
|---|---|---|
| `master` (= `origin/master`) | то, что сейчас на сайте | не менялась |
| `security/hardening` | заголовки безопасности, ограничение чужих Blob-хранилищ, лимит поиска заказа, тихие логи ошибок, обновления Next/React/Blob/nodemailer/zod, тесты безопасности, **CI** | только локально, не отправлена |
| `feature/phone-ui-favorites` | баннер на всю ширину на телефоне, поиск в «Filtre», карточка «Vezi toate», избранное без аккаунта | только локально, не отправлена |

Ветки не пересекаются по файлам и сливаются без конфликтов (проверено на временной ветке: типы, линтер, 72 модульных теста,
77 интеграционных, сборка и проверка сборки проходят).

## 2. CI (`.github/workflows/ci.yml`)

Три обязательные проверки, ни одна не использует production-секреты:

1. **quality**: `typecheck`, `lint`, модульные тесты, `npm audit --audit-level=critical` (high только для информации).
2. **integration**: `npm run test:integration`. Поднимает одноразовую MongoDB (replica set) на самом runner'е, накатывает схему и
   демо-каталог, запускает все `tests/*.integration.test.ts`. **Падает**, если хоть один тест пропущен, не запущен или упал, или
   запущено меньше тестов, чем объявлено в файлах (`node --test` считает пропущенный набор успехом, поэтому нужна эта проверка).
3. **build**: `npm run ci:build`. Сборка на одноразовой базе без Blob-токена, затем `tests/security.test.ts`
   (секреты и карты кода в сборке); эти тесты обязаны выполниться.

Необязательный секрет `TEST_DATABASE_URL`: если задан, используется он (имя базы должно содержать `test`, и она не может совпадать с
`DATABASE_URL`; иначе скрипт отказывается работать). Для CI на GitHub **не рекомендую** использовать для этого Atlas: адреса runner'ов
меняются, пришлось бы открыть доступ со всех IP. Одноразовая база в runner'е безопаснее и ничего не требует от вас.

Не проверено: первый запуск на GitHub (локально проверено на Windows с готовой тестовой базой; запуск на Linux с одноразовой базой
подтвердит первый прогон). E2E-тестов в проекте нет (не добавлял).

## 3. Что ещё не на production и риски

Не на production: всё из `security/hardening` и `feature/phone-ui-favorites`.

| Изменение | Возможная регрессия | Как проверить |
|---|---|---|
| Заголовки безопасности | Ломается встраивание сайта в чужие страницы (так и задумано); форма, отправляющая данные на чужой адрес | Главная, меню, товар, корзина, вход, админ-логин открываются без ошибок; в Network есть 7 заголовков |
| CSP `Report-Only` | Ничего не блокирует. Preview-сборки Vercel добавляют свой скрипт обратной связи `vercel.live`: сообщения о нём в консоли Preview ожидаемы | В консоли Chrome нет `[Report Only]` про ваши страницы |
| Ограничение картинок своим Blob | Если токена нет в окружении сборки, остаётся прежнее поведение (безопасный запасной вариант). Если id в токене не совпадёт с хостом картинок, они перестанут оптимизироваться | Фото каталога и загрузка фото в админке; `/img?u=<чужое Blob>&w=640&q=75` отвечает 400 (адрес проверяет `lib/image-optimizer/params.ts`) |
| Лимит поиска заказа (15 за 10 мин на адрес) | Покупатель за общим NAT может упереться в лимит (маловероятно) | Поиск заказа работает; после 15 неверных попыток сообщение «Prea multe încercări» |
| Next 16.4.2, React 19.3.1, @vercel/blob, nodemailer, zod | Любая регрессия сборки, почты, загрузки | Сборка Preview; письма (`npm run mail:check` на тестовой почте); загрузка фото |
| Избранное для гостей | Только `localStorage`; слияние при входе | Сердечко без входа; после входа список переносится в аккаунт |

Авторизация, каталог, корзина, оформление заказа, админка и Telegram **кодом не менялись** (кроме сообщений об ошибках в логах),
но попадают под сборку с новыми зависимостями: проверить регрессию нужно именно на них (см. план ниже).

## 4. План проверки Preview

Перед началом выясните в Vercel → проект → Settings → Environment Variables, **какую базу и какие ключи видит Preview**.
Если у Preview тот же `DATABASE_URL`, что и у Production, тестовый заказ на Preview попадёт в production-базу (с пометкой demo) и
отправит сообщение в Telegram. Для Preview лучше отдельная база или отключённые `TELEGRAM_*`/почта.

1. Отправить ветку (только с вашего разрешения): `git push origin security/hardening`. Vercel соберёт Preview, GitHub запустит CI.
2. Убедиться, что CI зелёный (все три задачи).
3. На Preview-адресе:
   - Заголовки: `curl -sI <preview>/` должен показать `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
     `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Content-Security-Policy`, `Content-Security-Policy-Report-Only`.
   - Консоль Chrome на главной, меню, странице товара, корзине, `/account/login`, `/admin/login`: нет красных ошибок и нет `[Report Only]`
     про ваши страницы.
   - Каталог на ro/ru/en; фото товаров; корзина (добавить, изменить количество).
   - Вход клиента; Google-вход (если настроен для Preview-адреса: иначе не проверять); вход админа; изменить флаг товара и вернуть.
   - Загрузка фото в админке; фото открывается.
   - Оформление заказа: **только если Preview изолирован** (см. выше). Иначе остановиться на последнем шаге перед отправкой.
   - Поиск заказа: 16-я неверная попытка с одного адреса блокируется.
4. Только после этого слить в `master` (Pull Request), затем следить за Production (шаг 6).
5. Полную CSP перевести из `Report-Only` в принудительную только после нескольких дней без сообщений: заменить ключ
   `Content-Security-Policy-Report-Only` на `Content-Security-Policy` в `lib/security-headers.ts`.

### Защита Preview в коде (`lib/preview-guard.mjs`)

Действует только при `VERCEL_ENV=preview`; Production и локальная работа не меняются.
- **Сборка:** `scripts/check-env.mjs` завершается ошибкой, если `DATABASE_URL` не указывает ровно на базу `fastburgers_preview`
  (имя читается из пути адреса MongoDB, сравнение строгое: без регистра-обходов, суффиксов, закодированных символов, лишних сегментов;
  имя в пароле, хосте или параметрах не засчитывается). В лог попадает только причина, не адрес.
- **Заказы:** если база не прошла проверку, `placeOrder` отказывает до обращения к базе (и `createOrder` бросает ошибку для любого другого
  вызова). `ORDER_MODE=live` в Preview игнорируется: заказы Preview всегда помечены demo.
- **Каналы:** Telegram, почта (включая письма о заказах и сброс пароля) и запись/удаление в Blob выключены в Preview даже при заданных
  переменных. Фото каталога по-прежнему показываются (публичные адреса).
- **Ограничения:** защита не знает, какой кластер за адресом: база с именем `fastburgers_preview` на чужом кластере её пройдёт.
  Отдельный пользователь Atlas с правами только на эту базу остаётся обязательной второй линией. Защита не заменяет настройку
  переменных в Vercel: пока Preview-значения не заданы, сборка Preview падает (это ожидаемо).

## 5. Откат

- Быстрее всего: Vercel → Deployments → предыдущий успешный деплой → меню «⋯» → **Instant Rollback** (откат без пересборки).
- В Git: `git revert <коммит>` и новый деплой (откат лучше делать отдельным коммитом, а не переписыванием истории).
- Только заголовки: убрать строку `securityHeaders(),` в `next.config.ts`.
- Только картинки: вернуть `hostname: "*.public.blob.vercel-storage.com"` в `next.config.ts`.
- Зависимости: вернуть `package.json` и `package-lock.json` из `master`, выполнить `npm ci`.
- Данные: этот набор изменений не меняет схему базы и данные.

## 6. Production после слияния

Проверить за первые 30 минут: сайт и фото, вход админа, заказ тестового клиента, который вы сами оформите и отмените (с пометкой
demo, если `ORDER_MODE` не `live`), письма, Telegram. В Vercel → Logs: нет всплеска 5xx и ошибок `Server Action`.

## 7. Действия во внешних панелях (выполняете вы)

### 7.1. Ротация токена Vercel Blob (токен вставлялся в чат)
1. **Не создавайте новое хранилище**: у него другой адрес, и все ссылки на фото в базе перестанут работать.
2. Vercel → Storage → ваш Blob store: найдите перевыпуск (regenerate) токена чтение-запись. Если в интерфейсе такого пункта нет,
   откройте поддержку Vercel (иначе остаётся только перенос всех файлов в новое хранилище и обновление ссылок в базе: отдельная задача).
3. Обновите `BLOB_READ_WRITE_TOKEN` в Vercel → Project → Settings → Environment Variables для Production, Preview, Development (если
   интеграция не обновляет её сама). Пересоберите проект (Redeploy).
4. Проверьте: фото каталога открываются, в админке загрузка фото работает.
5. Обновите значение в локальных `.env` и `.env.atlas`. Старый токен после этого не должен работать: проверьте загрузку со старым.
6. Идентификатор хранилища и публичный ключ webhook секретами не являются.

### 7.2. MFA
- **GitHub**: аватар → Settings → Password and authentication → Two-factor authentication (приложение-аутентификатор или passkey),
  сохраните коды восстановления в менеджере паролей. Репозиторий → Settings → Collaborators: оставьте только нужных. Settings →
  Branches → правило для `master`: обязательный Pull Request, обязательные проверки CI (`quality`, `integration`, `build`), запрет
  force-push. Settings → Code security: включите Secret scanning и Push protection, Dependabot alerts.
- **Vercel**: Account Settings → Security: добавьте passkey или приложение-аутентификатор и сохраните резервные коды. Для команды
  (если есть) проверьте, у кого есть доступ и роли. Project → Settings → Deployment Protection: защита Preview (например, вход через Vercel).
- **MongoDB Atlas**: профиль → Security → Multi-factor authentication; для организации (если она есть): Organization Settings →
  Security → Require MFA.

### 7.3. Права и сеть Atlas, бэкапы
- Security → Database Access: у пользователя приложения должна быть роль только на нужную базу (`readWrite` на `fastburgers`),
  без `atlasAdmin`/`dbAdmin` на все базы. Отдельный пользователь для скриптов, пароль у каждого свой.
- Security → Network Access: список IP. Vercel без статических адресов требует `0.0.0.0/0`. Это компромисс: тогда защита опирается на
  сложный пароль, права роли и MFA аккаунта Atlas. Если на вашем плане есть Private Link или статические IP Vercel, переходите на них.
- Бэкапы: Database → Backup. Автоматические Cloud Backup доступны на платных кластерах (на бесплатном M0 их нет: тогда регулярный
  экспорт `mongodump` или JSON-копия хранятся вне Atlas). **Проверьте восстановление** в отдельной тестовой базе, а не в production.
- Alerts: включите уведомления на вход с новых IP, всплеск подключений, нехватку места.

### 7.4. Firewall и защита от ботов (Vercel)
- Project → Firewall: правила ограничения запросов (rate limiting) для `/account/*`, `/admin/login` и серверных действий, а также
  режим Attack Challenge Mode на случай атаки. Набор правил зависит от тарифа: смотрите, что доступно.
- Защита от ботов (managed rules / BotID) как отдельная опция, если нужна для заказов.
- Vercel Security Checkpoint уже срабатывал на частые запросы с моей машины, то есть платформенная защита работает; её настройки я не видел.

### 7.5. Отдельная база Preview (`fastburgers_preview`)

1. Atlas → Database Access → Add New Database User: имя `fastburgers_preview_app`, пароль свой (не тот, что у боевого пользователя).
   Database User Privileges → Specific Privileges → роль `readWrite`, база `fastburgers_preview` (коллекция пусто). Других ролей нет.
   Temporary User выключен. Если есть Restrict Access, ограничьте вашим кластером.
2. Локальный файл `.env.preview` в корне проекта (игнорируется Git, значения никому не отправлять):
   `DATABASE_URL` (как боевой, но с этим пользователем и `/fastburgers_preview?retryWrites=true&w=majority`), `ADMIN_EMAIL`,
   `ADMIN_PASSWORD` (отдельный администратор Preview, от 12 символов, 3 класса знаков). Пароль с `@ : / ? # %` кодируется в адресе.
3. `npm run db:check:preview` (чтение: структура файла, ping, список коллекций) → `npm run db:push:preview` (схема, индексы) →
   `npm run db:seed:preview` (вымышленные данные). Скрипт `scripts/preview-db.mjs` ничего не запускает, пока адрес не указывает точно на
   `fastburgers_preview`, пользователь/пароль совпадают с боевыми из `.env.atlas` или нет `--confirm-preview`.

## 8. MFA администратора (не включено, дизайн)

Пока не проверены восстановление доступа и совместимость с сессиями, в код не добавлялось. План:
- TOTP (RFC 6238) и 8 одноразовых кодов восстановления (хранятся только хешами); секрет шифруется ключом из `AUTH_SECRET`.
- Режим `ADMIN_MFA=off|optional|required`. Сначала `optional`: у администратора появляется настройка, действующие сессии
  (`sessionVersion`) остаются валидными.
- Аварийный вход: скрипт `admin:grant`/сброс (как у пароля), требует доступа к серверу и базе; код восстановления в хранилище паролей.
- Тесты: неверный код, повтор кода, перебор (лимит), потеря устройства, совместимость со старой сессией, смена пароля.
- Включать `required` только после проверки на Preview и входа второго администратора.
